# DirBridge 版本规划

关联：[[00-总体技术方案]]、[[01-第一阶段MVP]]、[[02-架构与分层]]

## 目标

本文定义 DirBridge 后续 Git、GitHub 和版本发布的管理方式。

当前项目仍处于第一阶段 MVP 开发期。第一阶段完成前，重点是本地稳定开发、阶段性提交和完整验证；第一阶段完成后，再将仓库推送到 GitHub，并开始使用 GitHub Issues、Milestones、Pull Requests 和 Releases 管理后续版本。

## 分支策略

### `main`

`main` 是稳定主线。

进入 `main` 的代码必须满足：

- 当前阶段功能闭环。
- 能完成构建。
- 核心检查和相关 smoke test 通过。
- 文档已同步。
- 不包含临时代码、调试输出或未说明的破坏性变更。

`main` 不作为日常草稿开发分支。开发中的功能应先放在 `feature/*` 或 `fix/*` 分支。

### `feature/*`

`feature/*` 用于新增功能或阶段性能力开发。

命名示例：

```text
feature/mvp-file-panel-session
feature/transfer-control
feature/remote-session-tabs
feature/site-manager
```

推荐流程：

```powershell
git switch main
git switch -c feature/transfer-control
```

开发完成并验证后：

```powershell
git add .
git commit -m "实现传输任务取消与重试"
git switch main
git merge feature/transfer-control
```

推送到 GitHub 后，推荐使用 Pull Request 合并：

```text
feature/xxx -> Pull Request -> main
```

即使是个人项目，也可以使用 Pull Request 记录功能说明、测试结果和合并历史。

### `fix/*`

`fix/*` 用于修复已经进入 `main` 的问题。

命名示例：

```text
fix/ftp-create-file-overwrite
fix/remote-refresh-state
fix/local-menu-delete
```

如果修复影响已发布版本，合并后应考虑发布 patch 版本，例如 `v0.3.1`。

### `docs/*`

`docs/*` 用于较大的文档整理。

小范围文档更新可以跟随功能分支一起提交，不必单独开分支。

## 提交策略

提交不要求非常细碎，但必须是一个清晰的阶段点。

推荐粒度：

```text
一个明确功能或阶段完成
+ 构建通过
+ 相关测试通过
+ 文档同步
= 一次提交
```

不推荐：

- 每改几行就提交。
- 多个未验证功能混在一个长期未提交工作区。
- 为了拆历史而强行重写已经稳定的 `main` 提交。

当前已进入 `main` 的历史提交保留，不重写。后续从当前开发阶段开始切换到规范流程。

## 版本号规则

DirBridge 采用语义化版本格式：

```text
v主版本.次版本.修订版本
vMAJOR.MINOR.PATCH
```

早期开发阶段使用 `v0.x.y`。

规则：

- `MAJOR`：重大不兼容变化或正式大版本。DirBridge 在正式稳定前保持 `0`。
- `MINOR`：阶段性功能完成，例如远程浏览、传输队列、多会话。
- `PATCH`：bug 修复、小优化、文档补充、打包修正。

示例：

```text
v0.1.0  项目骨架和基础依赖验证
v0.2.0  远程浏览和基础站点配置
v0.3.0  文件操作、传输队列、拖拽传输、多远程会话基础
v0.3.1  修复 v0.3.0 中发现的问题
v0.4.0  传输取消、重试、并发限制和失败恢复
```

## 第一阶段发布策略

第一阶段 MVP 完成前，不急于推送 GitHub。

第一阶段完成标准：

- 本地和远程文件面板主流程可用。
- FTP/SFTP 远程浏览可用。
- 远程新建文件夹、新建文件、删除、重命名可用。
- 单文件上传、下载可用。
- 拖拽上传、下载可用。
- 多远程会话 Tab 基础可用。
- 底部传输队列可显示任务状态。
- 日志和基础配置可用。
- 文档与测试命令同步。

第一阶段完成后，执行：

```powershell
git switch main
git merge feature/mvp-file-panel-session
git tag v0.3.0
```

随后推送 GitHub：

```powershell
git push origin main
git push origin v0.3.0
```

如果此前还没有 GitHub 远程仓库，应先创建 GitHub 仓库，再添加远程：

```powershell
git remote add origin <GitHub仓库地址>
git push -u origin main
git push origin v0.3.0
```

## GitHub 管理方式

推送到 GitHub 后，推荐启用：

- Issues：记录 bug、功能需求、测试问题。
- Milestones：按版本组织任务，例如 `v0.4.0`。
- Pull Requests：功能分支合并到 `main` 的记录和检查点。
- Releases：每个稳定 tag 对应一个发布版本。

推荐结构：

```text
main
  稳定主线

feature/*
  功能开发

fix/*
  bug 修复

tag
  v0.3.0、v0.3.1、v0.4.0

GitHub Release
  对应 tag 的发布说明和可下载产物
```

## Release 规则

每个 GitHub Release 必须对应一个 Git tag。

Release 内容应包括：

- 版本标题。
- 功能变更摘要。
- 修复内容。
- 已知问题。
- 验证结果。
- Windows 可运行包，若当前阶段已经提供打包产物。

Release 示例：

```text
DirBridge v0.3.0

功能：
- 新增本地/远程统一右键菜单。
- 新增远程文件操作。
- 新增传输队列基础。
- 新增拖拽上传/下载。
- 新增多远程会话 Tab。

验证：
- Debug 构建通过。
- CoreChecks 通过。
- FTP/SFTP 真实服务器验证通过。
- UI smoke test 通过。

已知问题：
- 暂不支持目录递归传输。
- 暂不支持传输取消、重试和并发限制。
```

## 后续版本规划

### v0.3.0 第一阶段 MVP 基础版

定位：文件面板交互、多远程会话和基础传输能力闭环。

内容：

- Qt Widgets 主界面。
- 本地文件浏览。
- FTP/SFTP 远程浏览。
- 本地/远程统一右键菜单。
- 本地基础文件操作。
- 远程基础文件操作。
- 单文件上传、下载。
- 拖拽上传、下载。
- 全局传输队列基础。
- 多远程会话 Tab。
- 日志和站点配置。

### v0.4.0 传输控制版

定位：让传输队列从“可显示、可执行”升级为“可管理”。

内容：

- 传输取消。
- 传输重试。
- 并发限制。
- 失败恢复。
- 传输队列操作按钮。
- 更清晰的失败信息。

### v0.5.0 会话管理增强版

定位：增强站点管理和多会话使用体验。

计划内容：

- 会话属性编辑。
- 会话分组。
- 多远程会话恢复。
- 当前 Tab 与 Session Manager 状态同步。
- 更完整的连接错误提示。

### v0.6.0 目录传输版

定位：从单文件传输扩展到目录级传输。

计划内容：

- 本地目录上传。
- 远程目录下载。
- 目录递归任务展开。
- 传输队列中显示目录任务进度。

### v0.7.0 发布打包版

定位：形成可分发 Windows 版本。

计划内容：

- Windows Release 包。
- 运行时依赖整理。
- 默认配置目录策略。
- Release 验证清单。
- GitHub Release 附件。

## 当前仓库处理建议

当前已有未提交的大批开发改动，建议整体归入一个功能分支：

```powershell
git switch -c feature/mvp-file-panel-session
git add .
git commit -m "完善文件面板交互与多远程会话"
```

验证通过后合并回 `main`：

```powershell
git switch main
git merge feature/mvp-file-panel-session
git tag v0.3.0
```

不要重写已经进入 `main` 的历史提交。从当前阶段开始按“功能分支 -> 验证 -> 合并 main -> tag -> GitHub Release”的方式管理。
