# 三方库管理

关联：[CMake 依赖方案](CMake依赖方案.md)、[运行环境说明](运行环境说明.md)

## 管理原则

三方库文件不提交到 Git。仓库只提交：

- `deps.lock.json`
- `scripts/setup_third_party.ps1`
- CMake 配置
- 文档

克隆仓库后通过脚本复原依赖环境。

## 目录结构

```text
third_party/
├── _downloads/
├── _source/
└── installed/
    ├── curl/
    │   ├── include/
    │   ├── lib/
    │   └── bin/
    ├── nlohmann_json/
    │   └── include/
    ├── ghostty-vt/
    │   ├── include/
    │   ├── bin/
    │   └── licenses/
    └── spdlog/
        └── include/
```

说明：

- `_downloads` 保存下载包。
- `_source` 保存解压后的原始源码或发布包。
- `installed` 是项目实际引用的安装态依赖。

CMake 只允许引用 `third_party/installed`，不直接引用 `_source`。

## 当前依赖

依赖版本锁定在 `deps.lock.json`：

- curl `8.20.0_5` Windows MinGW 预编译包。
- nlohmann/json `3.12.0`。
- spdlog `1.17.0`。
- Ghostty VT commit `46edeee407ff1cd15fb7db3837025386b2f3a327`，使用固定 SHA-256 的 `x86_64-windows-gnu` DLL，关闭 SIMD。

当前脚本准备的 libcurl 包面向 MinGW，包含 `libcurl.dll.a` 和 `libcurl-x64.dll`。如果使用 MSVC 构建，需要准备匹配 MSVC ABI 的 libcurl，推荐通过 `vcpkg.json` 中的 `curl[ssh]` 从源码生成 `libcurl.lib`。

MSVC 构建不要复用其他项目目录中的 `libcurl.lib`，也不要使用 MinGW 的 `libcurl.dll.a`。

仓库提供 `vcpkg.json` 作为 MSVC 依赖入口。使用 `windows-msvc-vcpkg-*` preset 时，vcpkg 会根据 manifest 从源码构建 `curl[ssh]` 及其 OpenSSL、libssh2、zlib 等依赖。

## 初始化命令

```powershell
powershell -ExecutionPolicy Bypass -File scripts\setup_third_party.ps1
```

Ghostty VT 不由通用依赖脚本下载或构建。准备好与 `deps.lock.json` 匹配的已验证产物后，使用项目脚本核对 DLL SHA-256 并复制头文件、DLL 和 MIT License：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\setup_ghostty_vt_local.ps1 -SourceRoot <Ghostty VT 构建输出目录>
```

Ghostty 源码、Zig、构建缓存和 DLL 实体仍位于忽略的 `build/`、`third_party/` 目录；Git 只记录版本锁定、接入代码、准备脚本和许可证要求。

强制重新下载和整理：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\setup_third_party.ps1 -Force
```

## Git 策略

`third_party/` 整体被 `.gitignore` 排除。这样仓库不会包含三方源码、头文件、lib 或 dll。

如果要迁移到新机器：

1. 克隆仓库。
2. 运行 `scripts/setup_third_party.ps1`。
3. 执行 CMake configure 和 build。
